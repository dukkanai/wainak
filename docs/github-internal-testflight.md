مرشح workflow يستخدم ملف `ci.yml` المسجل في main لتفادي اشتراط تسجيل workflow جديد على الفرع الافتراضي. طُبق المرشح على فرع التطوير فقط بعد مواءمة اختبارات التفعيل. لا يتطلب ذلك دمج main. يفصل المرشح مجموعات concurrency، ويعطل الإلغاء التلقائي للمهمة الموقعة، ويمنع مهام CI الأخرى من البدء عند اختيار `mac-internal`.

## الصلاحيات ومخاطر المستودع العام

أثبتت قراءة GitHub أن المستودع PUBLIC والفرع الافتراضي main. أُنشئت البيئة بموافقة منفصلة عند 09:33 UTC، وأُعيد التحقق من إعداداتها بعد حفظ الأسرار وقبل تفعيل المصدر. لم يغيّر هذا التعديل صلاحيات المستودع أو إعدادات البيئة.

إعداد البيئة الفعلي المعتمد للمالك الواحد: required reviewer واحد هو حساب المالك `dukkanai`، بالمعرف العام `255427171` الذي تحققنا منه عبر GitHub API. يكون `prevent_self_review: false` حتى يستطيع المالك الموافقة ولو بدأ التشغيل بالحساب نفسه، مع `can_admins_bypass: false`، وselected deployment branches لفرع التطوير المحدد وحده، دون tags أو wildcards. تبقى الموافقة اليدوية مطلوبة؛ السماح بالمراجعة الذاتية لا يوافق تلقائيًا على التشغيل. التفويض بإعداد البيئة ليس موافقة deployment: يراجع المالك SHA ويقر التشغيل، ولا ينفذ المساعد موافقة تلقائية نيابة عنه. GitHub يتيح مراجعي البيئة للمستودعات العامة على Free، ولا يتيح أسرار البيئة للمهمة قبل الموافقة. عقد الفحص يرفض غياب المراجع، أو تغيير هويته، أو إضافة مراجع آخر، أو تفعيل منع المراجعة الذاتية الذي يسد مسار المالك الواحد. [قواعد حماية GitHub environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

المهمة تقبل workflow_dispatch فقط، والمستودع والفرع وSHA المطابق والـ runner ثابتة. لا pull_request أو pull_request_target أو workflow_run لتشغيل المسار الموقع، ولا تحميل artifacts من تشغيل غير موثوق أو SDK/cache مشترك. جميع actions المستخدمة مثبتة بـ full commit SHA، وcheckout لا يحفظ Git credentials. لا تدخل مدخلات المستخدم في نص shell؛ تمر عبر env ثم تتحقق صيغ SHA ورقم build. ترفض المهمة debug logging المعروف. تُحجب مخرجات العمليات والاستثناءات الخام، وتبقى أسماء المراحل والأسباب الآمنة والمدة والرمز وحالة التنظيف.

هذه الحواجز لا تجعل كودًا خبيثًا داخل SHA معتمد آمنًا. فصل أسرار التوقيع وP8 إلى خطوات يقلل التعرض العرضي، لكنه ليس عزلًا أمنيًا بين العمليات على الجهاز نفسه. خطوة أو dependency خبيثة قد تسرق ما يتاح لاحقًا للمهمة؛ مراجعة المالك للالتزام وملفات workflow/dependency lock قبل السماح بالأسرار هي الحد الأساسي. هذا البديل لا يوفر فصلًا بين شخصين: اختراق حساب المالك أو موافقته على SHA خبيث قد يتيح الأسرار. تقييد الفرع وSHA وتعطيل admin bypass لا يحمي من سيطرة مهاجم على حساب المالك الإداري، القادر أيضًا على تعديل إعدادات الحماية. التوقف اليدوي يقلل التشغيل غير المقصود، لكنه ليس مراجعة مستقلة. تستخدم أوامر security كلمة مرور الاستيراد في argv على الجهاز المؤقت؛ لا تُسجل argv، لكن كودًا خبيثًا يعمل بالحساب نفسه قد يراها. لا نعتمد على masking وحده. [إرشادات GitHub للأمان](https://docs.github.com/en/actions/reference/security/secure-use).

كذلك شهادة Apple Distribution مرتبطة بالفريق وليست محصورة بهذا التطبيق. ومفتاح ASC الحالي Team/App Manager أوسع من حاجة الرفع؛ Team keys تشمل تطبيقات الفريق، بينما individual keys تتبع صلاحيات المستخدم وتطبيقاته. قبِل المالك هذا النطاق صراحة في موافقته على حفظ مواد التوقيع في GitHub بتاريخ 29 أكتوبر 2026. بديل أقل صلاحية هو حساب/مفتاح فردي بصلاحية Developer ووصول محدود للتطبيق إذا سمحت ترتيبات الحساب؛ لا ينشأ الآن، ويحتاج مراجعة طريقة authentication واختباراتها بدل تبديل القيم فقط. [نطاق مفاتيح Apple](https://developer.apple.com/documentation/AppStoreConnectAPI/creating-api-keys-for-app-store-connect-api)، و[طرق وأدوار رفع النسخ](https://developer.apple.com/help/app-store-connect/manage-builds/upload-builds).

يبقى تنظيف الملفات المملوكة متاحًا حتى لو فشل عقد البصمات أو الوصفة، مع استمرار قيود المضيف والمسار ومجموعة العمليات. التنظيف best effort عند القتل القسري للـ runner: لا يمكن ضمان تنفيذ finally أو always بعد انقطاع الجهاز. يعتمد التخلص النهائي حينئذ على الجهاز الافتراضي المؤقت لدى GitHub؛ لا توجد نسخ أسرار في artifacts أو caches. فشل الرفع أو تنظيف عمليته بعد اتصال الشبكة قد يعني أن Apple استقبلت النسخة بالفعل؛ يُحظر retry تلقائيًا، ويجب فحص ASC قبل أي محاولة أخرى.

## التحقق المحلي وحدوده

الاختبارات تستخدم ملفات اصطناعية فقط وتغطي كل مرحلة توقيع ورفع، والإيصال وبصمة IPA وسياسة internal-only والهوية والروابط الرمزية واختلاف أسماء Mac والتطبيع، ورفض فك Base64 غير الصالح أو المتجاوز للحد، ورفض إدخال مفاتيح Apple وkeychains إلى Git index حتى لو أضيفت قسرًا. تختبر أيضًا فشل تنظيف keychain مع منع إنشاء إيصال السماح، وعدم تسريب canary من stdout/stderr/argv/exception، واستمرار التمييز بين نجاح الأمر وفشل فحصه اللاحق.

هذه محاكاة Linux لمسار التوقيع. لم تُختبر هنا شهادة Apple حقيقية أو security/codesign أو أماكن اكتشاف profile في Xcode 26.4.1 أو export داخلي أو altool API authentication أو معالجة Apple. نجاح unsigned السابق لا يثبت هذه العمليات الجديدة. أول تجربة موقعّة لاحقة يتولى root تنسيقها وعرض SHA النهائي على المالك؛ لا يبدأها تنفيذ هذا التعديل. تبقى مهلة البناء المشتركة 40 دقيقة، وفحص الموارد وSDK مستمرًا دون تخفيف.

JWT مستقل محدد بطلب GET الدقيق، والتحقق من المسار يرفض أي تطبيق أو معاملات إضافية أو تحويل إلى مضيف آخر قبل التوقيع أو الشبكة. يعرض حالات AWAITING_UPLOAD أو PROCESSING أو FAILED أو COMPLETE، وأعداد الأخطاء والتحذيرات وتصنيفات ثابتة وأكواد من قائمة محددة فقط. النصوص والأسماء والمسارات والروابط وقيم الأكواد غير المعروفة لا تخرج من العملية. غياب تفاصيل اختيارية يمثل عددًا مجهولًا، وليس ادعاء صفر أخطاء. نجاح الاستقبال لا يُعد إتاحة TestFlight، ولا يسبب إعادة رفع تلقائي.
