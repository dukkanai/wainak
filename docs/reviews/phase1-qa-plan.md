## نطاق العمل والعزل

- فحص مستقل لفروع تطوير backend وFlutter، لا تعديل على main أو نشر أو دمج.
- بيانات اصطناعية فقط، لا بريد أو مستخدمين أو مدفوعات حقيقية.
- لا اتصال بقاعدة التشغيل، ولا مهاجرات أو تشغيل API على واجهة شبكة عامة.
- تسجل لكل نتيجة: commit كامل، الأمر، البيئة، الزمن، رمز الخروج، وعدد الفحوص وحدودها.
- المراجعة الساكنة ليست اختبار تشغيل؛ المحاكاة ليست إثبات أمان الإنتاج.
- النجاح في هذه الشريحة لا يغلق متطلبات المراسلة المشفرة والمتاجر والنسخ والعمليات.
- الخلل في وظيفة معلنة منفذة = FAIL. الوظيفة غير المنفذة = NOT RUN / OUT OF SCOPE
  مع منع ادعائها في الواجهة أو الوثائق، وتظل شرط إطلاق إذا كانت لازمة.
- P0: تسرب بين الحسابات/العلاقات، تجاوز مباشر للأهلية أو الحظر أو الموافقات،
  فعل حقيقي غير مصرح به أو إمكانية تشغيل وضع الاختبار كإنتاج بصمت.
- P1: خلل انتقال/تكرار/تزامن، تعطيل وسيلة سلامة، ادعاء مضلل، أو عائق وصول أساسي.
  لا يسمي هذا التصنيف مراجعة اختراق كاملة.

## متطلبات إطلاق لا تغلقها هذه المرحلة

مصادقة وبريد حقيقيان ومقاومة انتحال الهوية؛ معاملة PostgreSQL وصلاحيات ومهاجرات
مختبرة؛ تشفير ومفاتيح وتسليم بين هاتفين؛ StoreKit/Play Billing واستعادة المشتريات؛
حذف الحساب وطلب حذف ويب ومصفوفة الاحتفاظ؛ مخزن أدلة مشفر معزول وصلاحيات وحذف؛
تشغيل البلاغات والاعتراضات وفريقه؛ ضمان العمر ومتطلبات حماية الأطفال في المتاجر؛
منع تعارف عشوائي/مجهول بمعنى سياسات المتاجر؛ خصوصية/Data safety/تعريف SDK؛
اختبار الأجهزة الفعلية؛ نسخ مشفرة خارج المضيف وجدولة وتنبيهات وتجربة استعادة/نقل.
لا تكون الميزات الأساسية للسلامة محصورة خلف شراء.

## طريقة الإثبات

1. تثبيت commit المرشح وقراءة diff دون تعديل شجرة المطور.
2. تشغيل فحوصه المعلنة داخل بيئة تطوير معزولة بعد مراجعة الأوامر.
3. إضافة اختبارات خصومية مستقلة في مساحة QA فقط عند إمكانها دون خدمات حقيقية.
4. تسجيل P0/P1 فورًا وإرسال reproduction للمطور؛ إعادة فحص commit الإصلاح لا الاكتفاء بالوعد.
5. حفظ التقرير النهائي مع PASS / FAIL / NOT RUN لكل بند داخل نطاق الشريحة.
6. لا إنهاء المراجعة على خطة أو اختبارات معلقة؛ يبقى انتظار المرشح/الإصلاح نشطًا.
